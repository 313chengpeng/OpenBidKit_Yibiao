# 需求介绍
这段内容是给你看的，有助于你更清晰的了解开发目的，不用把我说的话都写到程序中：
- 知识库是用户上传的有参考价值的历史资料，我们要对知识库进行整理分析，以便之后生成标书技术方案的时候，可以参考之前的资料。

# 知识库功能
- 页面应该是类似文件夹的样子，用户可以创建文件夹，并在文件夹内上传.doc.docx.wps.pdf.md文档。
- 将用户上传的任何文档都整理成markdown格式保存，这个要落到文件，以免之后丢失。
- 调用AI将文档内容整理成json格式，包括标题、简述和原文。
```
[{
    "id":"",
    "title":"",
    "resume":"",
    "content":""
}]
- 解析最好能有真实的进度条
```

# 知识库用法（这个先不用实现，只是便于你理解）
- 在生成目录阶段，传入[{"title":""}]给AI参考
- 生成正文的编排阶段，把`[{
    "id":"",
    "title":"",
    "resume":""
    }]`传给AI，让AI在编排阶段，确定每个子节点是否能应用到知识库中的内容，如果能用到，记录ID
- 在生成正文的时候，通过ID找到资料的正文，然后以参考资料的形式提供给生成正文的AI

# 优化1



上传资料时，用AI分析成知识条目库，这是现在的方案。但是分析的条目不准确，且丢失了很多内容。
我希望在分析阶段做以下处理：

1. 先让AI提取出有意义的知识条目（舍弃掉封面、目录等对写标书无意义的条目）。
2. 给正文按自然段编号，提交给AI
3. 让AI输出每个条目对应的段落编号
4. 程序根据AI输出结果，处理知识条目

目前我能想到的困难点有两个：
1. 第三步，AI分析条目对应段落编号时可能会漏掉部分段落，即有部分段落不属于任何条目，如何能做到让AI尽可能分析出所有段落所对应的条目
2. 如果AI能分析出所有段落对应的条目，那输出的内容会不会太多，超过AI输出上限？如何让AI分步执行以保证分析全面

---

结合你的方案我设计的流程如下：

1. 用程序筛掉封面、目录、页码、空行、页眉页脚、签章页等，直接筛掉，无需标记，不提交给AI就行了
2. 筛后的文档按自然段/表格/列表块编号
   例如：`P000001`、`P000002`、`P000003`。

3. 提交给AI，先让AI输出知识条目数组，仅包含ID、标题和摘要
4. 在页面中展示出AI返回的知识条目，总共多少条，用户录入一批分析多少条（因为我们现在不知道AI的能力上限，一次性提取所有段落，可能会有大量丢失，一次提取的太少又会有资源浪费，所以这是开发调试阶段的一个临时页面，让我们更好的测试出AI的能力）
5. 按照用户输入的条数，将知识条目分批，循环询问AI，投入分好段的全文、提取的部分id、标题、摘要json数组。然AI给这些数组匹配段落，仅返回id+段落号就行
6. 所有批次都执行完后，进行一次检查，判断是否有遗漏的段落，如果有，将完整知识条目id、标题、摘要和遗漏段落提交给AI，让AI再匹配一次，这次让AI返回匹配好的id+段落，再额外返回一个推荐舍弃段落和一个新增知识条目，即让AI分析这些遗漏短时是否有必要保留，被遗漏是否是因为没有合适的知识条目，如果是就新增条目，如果段落质量低没必要保留，就放到舍弃段落。这样所有遗漏段落就都有明确的标识了。
7. 把第五步和第六步的结果合并，看是否还有遗漏段落，如果还有再重复执行一次第六步。最多重复执行一次，再有遗漏就直接标记为舍弃。
8. 把前面执行返回的所有结果拼接成完整json
9. 用程序根据json进行正文提取，形成最终结果

# 定版流程



方案可以成立，我按你的取舍调整后，建议定版为下面这个流程。

**定版流程**
1. 程序预处理  
   直接筛掉封面、目录、页码、空行、页眉页脚、签章页等明显无价值内容。  
   同时保存 `filtered_blocks.json`，只用于调试，不进入 AI 分析。

2. 生成 block  
   对筛选后的正文生成 `block` 编号，例如 `P000001`。  
   block 类型包括 `paragraph`、`table`、`list` 等。

3. 第一次 AI 抽取知识条目  
   输入编号后的全文 block。  
   AI 只返回候选知识条目：标题、摘要，不返回正文，不返回 ID。  
   程序生成 ID，例如 `K000001`。

4. 第二次 AI 补充知识条目  
   输入全文 block + 第一次抽取出的条目标题摘要。  
   让 AI 判断是否有遗漏主题，并返回补充条目。  
   程序合并两次抽取结果，再统一编号。

5. 页面展示调试入口  
   展示：总 block 数、候选知识条目数、用户输入“每批分析多少条”。  
   这是开发调试阶段非常有必要的，可以用来摸模型能力上限。

6. 分批匹配段落  
   每批提交：全文 block + 当前批次知识条目。  
   AI 只做强相关匹配，不要求覆盖全部 block。  
   AI 返回 `id + ranges`。

7. 检查遗漏 block  
   程序合并所有批次结果后，找出没有被任何知识条目引用的 block。

8. AI 兜底补漏  
   输入：完整知识条目列表 + 遗漏 block。  
   AI 必须把遗漏 block 分成三类：匹配已有条目、新增知识条目、推荐舍弃段落。

9. 最多补漏两轮  
   第一次补漏后再检查遗漏。  
   如果仍有遗漏，再重复一次补漏。  
   第二次后仍遗漏的 block 放入 `system_discarded_after_retry`。

10. 程序生成最终结果  
   程序合并所有 AI 返回结果，根据 block 编号回填正文，生成最终知识条目库。

**AI 返回格式建议**
分批匹配返回：

```json
{
  "matches": [
    {
      "id": "K000001",
      "ranges": [["P000012", "P000018"], ["P000026", "P000030"]]
    }
  ]
}
```

补漏返回：

```json
{
  "matches": [
    {
      "id": "K000001",
      "ranges": [["P000080", "P000083"]]
    }
  ],
  "new_items": [
    {
      "title": "项目风险应对措施",
      "summary": "描述风险识别、响应机制和应急处理流程",
      "ranges": [["P000090", "P000095"]]
    }
  ],
  "discarded": [
    {
      "ranges": [["P000100", "P000102"]],
      "reason": "内容为低价值格式文本"
    }
  ]
}
```

**我建议额外保留的处理报告**
- `total_blocks`
- `filtered_blocks_count`
- `candidate_items_count`
- `matched_blocks_count`
- `discarded_blocks_count`
- `system_discarded_after_retry_count`
- `new_items_from_recovery_count`
- `coverage_rate`

**需要注意的一点**
第 5 步“全文 block + 当前批次知识条目”会反复提交全文，成本和上下文压力较大，但开发调试阶段可以接受。等效果验证后，再优化成“全文摘要索引 + 相关 block 候选”也不迟。

**我的结论**
这个方案可以作为下一版知识库分析流程实施。关键点是：AI 只负责抽条目和匹配编号，程序负责编号、合并、补漏、回填、报告，避免正文丢失。

## RAG 检索模式

### 设计目标

在保留原有「AI 抽取条目 + 段落匹配」流程的同时，新增「文档向量化 + 实时检索」模式，供用户按文件夹粒度选择：

- `extraction`（默认）：原有流程，AI 抽条目、段落匹配、用于在 Step03/04 注入参考资料。
- `rag`：把文档切分成 Chunk、向量化入库；生成目录 / 正文时实时按 query 检索相关片段。

两种模式互不影响，可在同一个工作区同时存在多个文件夹，分别选用不同模式；调用方在 Step03/Step04 把 RAG 命中片段和原条目库合在一起喂给 AI。

### 物理存储

`sqliteDatabase.cjs` 在 `knowledge_documents` / `knowledge_items` 之外新增以下表与字段：

- `knowledge_documents` 增加：
  - `chunk_count` `embedded_chunk_count` `embedding_model` `embedding_dimensions` `embedding_updated_at`：记录 RAG 模式下当前文档的向量化进度、所用模型与维度。
- `knowledge_folders` 增加：
  - `mode` `embedding_model` `embedding_dimensions`：记录文件夹的检索模式与默认 embedding 配置。
- `knowledge_rag_chunks`（新表）：`document_id` `chunk_id` `heading_path` `content` `content_chars` `token_estimate` `embedding`（BLOB）`embedding_model` `embedding_dimensions` `sort_order`。
  - `embedding` 字段以 Float32 LE 字节数组持久化；`dimensions` 与 `embedding_dimensions` 必须严格一致，运行时通过 `deserializeVector` 反序列化。
  - `heading_path` 由 Markdown 解析得到，检索结果会把它作为片段标题回传给 Renderer。
- `knowledge_rag_chunks` 索引：`(document_id, sort_order)` 与 `(embedding_model)`，提高按文档读取和按模型筛选效率。

### 文档处理流水线

RAG 模式下的文档处理按以下顺序执行（`documentProcessor` 在模式为 `rag` 时分支）：

1. **复制源文件** → `workspace/knowledge/documents/{id}/source.{ext}`。
2. **格式转换** → Markdown，落盘到 `markdown`，与 `extraction` 模式共用。
3. **Chunk 切分**（新增 `chunking` 状态）：
   - 按 Markdown 标题层级切片，每个 Chunk 记录 `heading_path` 与 `content`。
   - 限制单 Chunk 字符数（默认 800），段落过长时强制切分。
4. **Embedding 写入**（新增 `embedding` 状态）：
   - 调 `embeddingService.embedBatch`，按配置 `batch_size` 分批。
   - 向量通过 `serializeVector` 落盘为 BLOB，记录模型名和维度。
   - 失败时进入 `error`，保留已成功嵌入的 Chunk，重试只重跑未完成的 Chunk。
5. **状态进入**：`success`（RAG 模式下不再有 `extracting` / `matching` 步骤）。

进度条与状态事件由 `knowledgeBase.onEvent` 推送，前端 KnowledgeBasePage 根据 `activeFolder.mode` 切换文档卡显示：

- `extraction`：`条数 / 候选 / block`。
- `rag`：`chunk 数 / 已向量数 / embedding_model`。

### 检索流程

`ragService.search` 接收 `(query, documentIds, topK, minScore)`，执行：

1. 调 `embeddingService.embedOne(query)` 得到查询向量。
2. 仅在指定的 `documentIds` 范围内取出 RAG chunk，向量反序列化到 Float32 数组。
3. 计算余弦相似度 `cosine(query, chunk)`，过滤 `score < minScore` 的结果。
4. 按 score 降序取 `topK` 条，返回 `{ documentId, chunkId, headingPath, content, score, modelName }`。

为了避免每次重新反序列化全部 chunk，向量会在 `vectorIndexService` 进程内缓存：第一次访问某 `(model, dimensions)` 组合时一次性建索引，后续命中本地缓存。模型或维度变化时自动失效。

### 在生成流程中的接入

- **Step03 生成目录**（`outlineGenerationTask.cjs`）：
  - 当 `payload.reference_knowledge_document_ids` 中包含 RAG 模式文档时，按文件夹分组调 `knowledgeBaseService.searchRag`。
  - 检索 query 拼接为 `项目概述 + 技术要求 + 已有的一级目录标题`，每个文件夹默认 `topK=6`。
  - 把命中片段以 `RAG-N` 形式注入 prompt 的「参考知识库」段落，与原有条目并列。
- **Step04 生成正文**（`contentGenerationTask.cjs`）：
  - 在为某个章节收集参考时，先按 `reference_knowledge_document_ids` 收集条目，再合并 `content_rag_ids` 命中的 Chunk。
  - Chunk 同样以 `参考资料-片段` 形式进入 prompt，并标注 `文档 / 章节标题` 方便 AI 引用。
  - RAG 与原条目都不可用时回退到仅依赖目录 + 全局事实。

### 用户界面

- **设置 → Embedding 模型**：新增「Embedding 模型」配置页卡，填写 provider、base_url、api_key、model_name、dimensions、batch_size、request_mode；「获取」按钮调用 `ai:list-embedding-models` 请求 `${baseUrl}/models` 拉取可用模型列表，命中后切换为下拉选择并在列表为空时保留文本输入；「测试」按钮调用 `ai:test-embedding-model` 真实跑一次 `embeddings` 接口。切换 provider 或修改 base_url / api_key 时自动清空已拉取的模型列表。
- **知识库文件夹创建弹窗**：在原名称输入框下方加一组模式按钮「条目匹配 / RAG 检索」，选中后给 RAG 模式附加说明文案。
- **文档卡**：模式为 RAG 时显示 Chunk 进度、已向量数、embedding 模型名；模式为条目匹配时仍显示旧字段。
- **参考知识库面板**（`OutlineEditPage`）：在已有「轻量条目」之上叠加 RAG 命中片段组，每个文件夹可独立配置 query 和 topK；条目命中和 RAG 命中按文件夹分组展示，可同时勾选。

### 失败与重试

- Embedding 调用失败：文档进入 `error`，保留 `chunk_count` 与已向量的 Chunk 数量。点击「重试」从最近一次未完成的 Chunk 继续。
- 模型变更：用户切换 Embedding 模型后，对历史 RAG 文档提供「重新向量化」入口（`reembedRagDocument`），按当前模型批量重跑并覆盖写入。
- 维度不一致：写入时校验 chunk 向量维度与文档 `embedding_dimensions` 一致；不一致则记录 `last_error` 并提示用户重试。

### 与「条目匹配」模式的隔离

- 同一文档在两种模式下互不干扰：模式由所属文件夹决定，文档处理流程按 `folder.mode` 分支。
- Step03/04 同时支持两种来源，prompt 中会标注「条目来源：extraction」或「条目来源：rag」以便审计。
- 数据库迁移（v2 → v3）保留原 `extraction` 模式数据；RAG 模式表从空开始，用户上传新文档后才会产生数据。
